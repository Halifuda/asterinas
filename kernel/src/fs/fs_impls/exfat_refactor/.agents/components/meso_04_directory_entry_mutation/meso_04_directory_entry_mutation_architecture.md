# Meso 04: `directory_entry_mutation` Architecture

## 1. Meso-Component Definition
- **Component**: `directory_entry_mutation`
- **Macro-Owner**: `ExfatInode(dir)`
- **Responsibility**: Owns write-side namespace mutation for exFAT directories, including entry-set slot acquisition, creation of new file or directory entry sets, deletion ordering, cross-directory rename sequencing, emptiness-gated overwrite/removal refusal, and the mutation-side typed boundaries for unrecognized directory entries, while leaving read-side lookup identity reconstruction to `meso_03_directory_lookup_and_identity` and mount-global allocator accounting / volume-state posture to sibling `ExfatFs` meso components.

## 3. Static Lock Boundaries
- **Expected Inlet State**:
  - `create`, `mkdir`, `unlink`, `rmdir`, and `rename` must enter from `ExfatFs state rwlock(Write/intend-mutate)` with the participating directory `ExfatInode rwlock(Write)` set admitted in the frozen stable order.
  - When two directory inodes participate, callers must arrive in the accepted multi-inode order derived from durable identity; this meso must not invent an ad hoc rename-only ordering that conflicts with `macro_00_global_topology`.
  - Callers must not arrive holding `ExfatFs allocator rwlock`; allocator participation for directory growth, target reclamation, or removed-object cluster release remains subordinate to the directory-mutation boundary.
  - Read-side lookup identity or alias state from `meso_03_directory_lookup_and_identity` may be consulted only as already-established neighbor truth; this meso does not begin from lookup-owned read locks or republish read-side identity rules as its own inlet.
- **Topology Placement**:
  - Highest lock level permitted to acquire internally: `Level 4` (`ExfatFs allocator rwlock`), after entering through `Level 1` and the ordered directory `Level 2` inode locks, with optional directory stream-extent coordination at `Level 3` when slot growth or directory-stream shape changes require it.
  - Prohibited dependencies: `Cannot begin from allocator-held or stream-held context`; `cannot acquire any lock above ExfatFs state rwlock`; `cannot absorb file-content mutation, file-scoped sync, or read-side lookup semantics that belong to sibling meso components`.

- Reuses the stable naming truth, identity-by-directory-entry-location, and lookup-side anomaly interpretation from `meso_03_directory_lookup_and_identity`, but owns the write-side consequences when names or entry locations are created, removed, or moved.
- Imports allocator authority, free-space truth, online discard posture, and recount boundaries from `meso_02_free_space_accounting_and_discard`; this meso may require cluster growth or reclamation, but it must not redefine `AllocationBitmap` / FAT accounting ownership.
- Imports mount-wide anomaly posture and the global `VolumeDirty` persistence bracket from `meso_08_filesystem_sync_and_volume_state`; this meso keeps only its local namespace-ordering facts and must not redefine mount-wide dirty/clean transitions or forced-shutdown state machines.
- Supplies namespace-mutation and entry-location rewrite boundaries that later `meso_09_file_metadata_projection_and_update` and `meso_10_directory_metadata_projection_and_update` must preserve when they update metadata on already-identified objects.
- Shares stream-shape consequences with `meso_06_file_content_mutation` only at the structural edge where a rename or deletion reaches a file-owned Stream Extension / cluster chain; ordinary file content growth, shrink, and `ValidDataLength` rules remain outside this meso.
